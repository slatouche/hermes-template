# Work planning

## When to Use
Use when turning an agreed plan into cards, when a card comes back blocked or in triage, when `manager-watch` wakes you, when the Optimiser's proposals arrive, or when a feature is ready for the owner's sign-off. The card format and the builder's rules are in `AGENTS.md` (every bot loads them); this skill is how you, the Manager, use them. Detail lives in `references/`: `checks.md` (writing checks that prove something), `kanban-cli.md` (CLI shapes, boards, who gets notified), `real-input-verification.md` (driving a control like a person), `live-update-verification.md` (proving a page updated without reloading).

## Builds: code goes live once per build, by script
Every change to the app's code is a **build**: one branch, the cards that make it, then **one** check and **one** landing, both done by `~/.hermes/scripts/build.py` (no bot runs for them). You decide what one build is: a feature, an agreed design, or a lone fix (a build of one).
- `build.py start <slug> --title "<what>"` makes the branch (`build/<slug>`) and its worktree (`~/wt/<slug>`) from main and prints the two things every card of the build carries: the line `Build: <slug>` in its body and `--workspace dir:<worktree>`. Cut the cards (below), then `build.py ready <slug>`.
- **Each card** does its part and runs only **its own** checks, then commits on the branch. No per-card review, full suite, merge, restart or land card.
- **When every card is done**, the build-tick timer (every 30 s) runs `build.py`: main merged into the branch, the full suite once, every card's checks again; for an agreed design, the **look check** too (`dv.py look`: each screen of the build against the agreed mockup, by the design view's headless browser). Then the reviews it needs, each once for the whole build and only if that bot is hired: a **Designer look review** only when screens still differ, a **Tester review** only if a card says `Review: tester`. Then it merges into main, restarts the app's services and runs the cards' `(live)` checks against the running app. Anything failing: one Engineer card with all of it, on the same branch; the build re-checks itself when that's done. A live check failing puts main back to where it was. The third failure comes to you (`Build <slug> keeps failing`, the build stops): fix the check, re-slice or try a new angle, then `build.py ready <slug>`, or `build.py abort <slug>`.
- `build.py status` shows every open build, its stage and its cards. The build's history (each stage and how long it took) is what the Optimiser reads.

## Cutting cards
0. **Route by who owns it, one card, no relay.** A UI change the owner asks for (look, layout, wording, what a screen shows) belongs in the design view: point them there (or send it as a note yourself), and it lands in seconds; once agreed it's built with the rest. No card, no Tester. A code fix or a feature is an **Engineer** card. **Building is never the Tester's job:** no Engineer yet and real code to write? Propose hiring one rather than handing it to the Tester or the Designer. Small choices inside a request are the bot's to make (it says which it picked).
1. **Say the shape on the first line** (`Shape: quick | scoped | needs_owner | needs_breakdown`). Only you create `needs_breakdown` cards, and you cut them into `quick`/`scoped` cards; a worker that finds its card bigger than it looked stops and messages you one line (`needs_breakdown: <what is really in it>`). Bots self-card only `quick` work in their own domain. Several similar quick jobs **collate into one card with a checkbox list**, each item with its own check. The handoff's first line says what the shape turned out to be (`quick as carded` / `bigger: needed the funnel`).
2. **One outcome per card, smallest first, about 15 minutes: 30-60 steps** (a bot has 90; hitting the cap resumes but costs a restart). A bot works one card at a time, so a long card holds up everything behind it. A build across several screens is a card per screen, in order, on one `Session:` topic; so is work that crosses layers (storage, serving, loading data, a service and its review link). Slice 1 is a plain card (no goal mode). If you can't write the Verification, the card isn't ready: ask, prototype or research first.
3. **Verification comes from the test plan** (`qa/<feature>/test-plan.md` when there's a Tester), copied verbatim; without one, write 2-5 checks yourself: a command and its exact expected output, plus one "reachable from the running app" check. Write each as a list item `` `<command>` → `<expected>` `` (the expected text is what the command prints; `exit <n>` for an exit code), and add `(live)` to the check that needs the running app: `build.py` runs the others in the build's worktree before merging and the live ones after. The rules that matter most (the rest in `references/checks.md`):
   - **Run each check yourself before it goes in the card** and note what it returns now. A wrong port, path or route is the common error.
   - **A check must be able to fail:** run it against the blocked case (a cover over the control, the build before the fix) and see it fail.
   - **A control the owner clicks or types into is proved with real input** (`ui-check.sh --click / --type`), never by assigning `.value` or calling `.click()`.
   - **Numbers before pictures.** A colour, size, gap, count or overflow is read from the DOM in one call; a look (`vision_analyze`, 30-60 s) only for what only a look answers, once, on the finished change, cropped.
   - **A layout complaint is reproduced at the owner's widths** (1280, 1100, 900, 760) before anything changes.
   - **No check depends on another card running**, and **no check writes into a real channel**: a test of the design view runs on a throwaway copy of it (`design-view.py --port <spare> --layer <a copy> --no-cards`), never the owner's; a fixture card goes on the `rig` board, blocked at creation, so it can never ring the owner. Close what a check created as part of the check.
4. **Design notes don't need cards:** the owner's notes in the design view are done there, in seconds, with no card. What reaches you from it: build notes (on the running list, below), behavior proposals to review, and the build after Agreed (see "The design view" below).
5. **Give related cards one `Session:` topic** (`<area>:<thing>`, e.g. `engineer:deck-view`) so the same bot resumes what it knows. Unrelated work, a new topic; a stale or confused topic, `Session: new <topic>`. A long session does slow later cards, but the fix is compaction (it summarises a big session, and tidies one 45 minutes after work stops), never a fresh topic for speed: if rounds on a big session stay slow, tell the owner and propose a lower compaction threshold. `~/.hermes/scripts/hermes-worker.py --topics` (with `HERMES_HOME` set to the bot's profile) lists them.
6. **Title at most 50 characters, no trailing punctuation** (the branch name is built from it).
7. **Settings:** `idempotency_key`; `max_runtime_seconds` 3600 for code, 1800 for research and docs; workspace `dir:<the build's worktree>` for code (the build's cards share it), `dir` on `~/workspace` for docs and vault work; `skills=[...]` only for task-specific skills. Don't pin a model on a card that goes to review. The title is positional on `create`; more in `references/kanban-cli.md`.
8. **Things the owner opens stay up.** A card that builds something the owner uses (an app, a page, an API) checks it from the owner's network (`http://<host address>:<port in the project's block>`) and runs it as a systemd user service (`Restart=always`, enabled; restarted after a change). The design view (`<API port + 51>`) already serves the front end from `main` with mock data, so design never touches real data; nothing to add per app. The real app gets no review link.
9. **Order with parents, not hope.** No two cards that can run at once own the same paths.
10. **Review by rule** (`Review:` in the card's Context line). **A bot runs only when the work needs it:** every review is a model run, a slot and minutes of wall clock, so a build gets **at most one** review, of the whole build, after the script's checks pass.

    | Work | Review |
    |---|---|
    | new behaviour, a state machine, data, money, files, migrations, permissions, print geometry, security | `tester` (if hired): one review of the build, against the test plan's cases |
    | UI from the agreed design, a colour, copy line, doc line, rule; other code | `none`: the cards' checks are the proof; for the agreed design, the look check is, and the Designer reviews only the screens it finds different |

    **The Tester tests what the software does:** use cases and the test plan's cases, posed so a run passes or fails. Whether a test plan includes a UI check (a control reachable, a flow that works at a width) is your call when you write the plan, and it is still a behaviour check (`ui-check.sh --click/--type`), never a judgement on looks. Never wake a bot to re-confirm a check the script already ran.
11. **Goal mode is the exception.** Only when it repeats, the budget allows, a command decides it, and the worker can run what it built; then `goal_max_turns: 6`, never on slice 1. Its judge reads only 2,000 characters of the card.

## Fixing a defect the owner reports
Card the **mechanism**, not the patch: name what let the bug through and change that (a hand-kept list every new panel must join becomes a structural rule; a check that assigned a value becomes one that types), and say which class of bug it prevents. Doing the same cleanup by hand a third time is the same signal. Two exceptions: when the owner is standing in front of the broken thing, fix and verify it yourself now and card only the hardening; when a card is still writing that file, comment on the card and re-check after it finishes.

## When work comes back
- **A build's cards:** nothing to do per card; `build.py` checks the whole build and puts it live (or makes the fix card). Look at `build.py status` when asked, and act only on `Build <slug> keeps failing`.
- **Other work done** (docs, vault, research): check every `Verified:` line against the card's Verification and that every promised output exists and isn't empty (`ls -l`). Missing, empty or vague: send it back with one line saying which. Also:
  - **What did the check leave behind?** If it sent, saved, answered or dispatched anything through a channel the owner uses (`ls -lt vault/raw/feedback/`, the board), stop any round it spawned (`hermes kanban complete <id> --force`) and withdraw it before telling the owner it landed.
  - **Are earlier fixes still there?** When the card touched a file another card recently fixed (a shared script, the overlay), grep the file and the copy actually served for the earlier fix: two workers on one file quietly undo each other.
  - **Resolve every path the handoff names** before acting on it: a one-off check script and the changed file read the same in a summary.
- **Blocked or in triage:** never loop a card a fourth time. Pick one: the check is wrong (fix it, with the owner's OK if they approved it); the card is too big (re-slice); the builder is stuck (a new card with a new angle, once); it needs the owner (one question with your recommendation, listed in `waiting_on_owner` in `00-status.md`).
- **Direct work you didn't plan** (a specialist carded it for the owner): fold it into the plan; no card id in the log, ask the bot to card it. Work the owner is doing **live in a chat** is never a `ready` card: it's `blocked` and the bot in the chat completes it.

## What needs the owner (think before you ask)
Ask only when the answer is theirs: **what the product should do or look like** (scope, taste, a trade-off between things they want), **money, risk or anything irreversible**, **something only a person can do** (a secret, a purchase, a login), or **a real gap** the vault, spec and past answers don't settle. The team decides the rest and records it: checks, technical choices inside an agreed spec, card order, fixes, tools. When a bot blocks for the owner on something that isn't theirs, answer it (or route it), comment why, and unblock. Unsure: decide, log a `decision`, carry on.

**One question at most, and only when the work can't go further without it**: a fork inside the change being made where both options are plausible and visibly different, or something the owner raised that reads both ways. Otherwise make the call, put it live, and say in one line what you decided. **Never an open invitation** ("what should I change next?" hands the deciding back). The same bar goes into anything that writes cards.

## The owner queue
Everything that needs the owner's decision, answer, approval or hands is **a card blocked as `needs_input`** (or `capability` for what only a person can do). One place, nothing lost, nothing times out.
- **Bots raise it:** `kanban_block(kind="needs_input", reason="<one question>. Options: ... I recommend ... because ...")`, then stop.
- **Ask the question, not the mechanism:** one plain question in the owner's terms, what "yes" does, your recommendation; paths and internals stay in the linked proposal. Short sentences: `owner-queue.py` joins the lines with spaces.
- **You raise approvals the same way:** a proposal (system change, hire, an Optimiser proposal, gate, design stop) gets one card, from a chat or a card alike: `hermes kanban create "Owner: <the decision>" --assignee manager --initial-status blocked --body "<context>"`, then `hermes kanban block <id> --kind needs_input "<the question, options, your recommendation>"`. A card that is merely `blocked` never shows in `/queue`; never make a second card whose only job is to block itself.
- **Verify what a proposal leans on before you ask** (the endpoint, the field, that the session really resumes): an approval on a wrong premise costs a second question.
- **Never chase:** no reminders or re-asking. `waiting_on_owner` in `00-status.md` lists the card ids.
- **Going through it:** when they ask "what needs me?" say `/queue` (`/usr/bin/python3 ~/.hermes/scripts/owner-queue.py`; it and `board-now.py` work in a chat, not inside a worker), then take items **one at a time**; batch answers are fine ("yes to 1 and 3"). Each answer: a comment on the card with their words, a `decision` log line, the change applied or the card unblocked. "Later" leaves it waiting.

## Passing on a design pick
**Design is visual; building comes after Agreed.** Everything new is seen first in the design view (placeholders, simulated screens, behaviors); the Engineer never prototypes. Only the owner's Agreed (or, in older projects, "build it") starts a build, planned as below.

## The design view (what reaches you from it)
The owner designs on `<API port + 51>`: notes are done there, in seconds, so they never become cards. The design view works out what the owner means from close-ups of what they pointed at (asking them when it isn't clear), makes the change, checks it and takes a final look; options never touch the mockup until one is picked. `/dv/dry-run` shows what a note would be taken to mean without changing anything (`tests/understanding_check.py` in the template scores it). Function points go on the running list (below); two things become cards:
- **`Review proposed behavior: <name>`**: a new interaction for the mockup that already passed `behavior-check.py` (safe, registers itself, sets up fast; one that fails never reaches you). What's left is fit: does it do what the note needs, as a reusable interaction? `dv.py approve <name>` or `dv.py reject <name> "<why>"`. A minute, no harness.
- **`Build the agreed design (<stamp>)`**: the owner pressed Agreed. The mockup is the main app with the visible changes they want; the build makes it real and working. The layer is frozen (it is the reference) and `build.py` has already made the build (`design-<stamp>`, its worktree named in the card). Plan it with the fewest bot runs that do it well:
  - **Read the build sheet** (`dv.py export`): what the owner asked, change by change in their words, and this round's build notes (the functions behind the look). Those notes are part of this build; the other open ones aren't unless the owner says (tell them in one line which could fit).
  - **Engineer cards, usually one per area of the app:** fold the look in exactly *and* make it work, in one pass (the role page says how: the export, the fold, the functions, `dv.py look`, `Look decisions:` for states the design didn't show). Give each card checks for what it makes work (`(live)` where it needs the running app) and the build notes it closes.
  - **No Designer card by default:** the look check runs by itself, and only screens that still differ get one Designer look review. Plan a Designer card only for a design decision the mockup left open, before the Engineer's card.
  - **Tester only where behaviour is worth a review** (saving, data, a multi-step flow), `Review: tester` on that card with its cases in `vault/qa/`; one review for the whole build.
  - **A change to the agreed look itself** (the build can't work as shown) is the owner's call: the Engineer blocks with the question, you put it to the owner with your recommendation.
  Then complete your card: that starts the build. It goes live on the main app by itself when its checks pass, the owner's mockup unfreezes onto it, and the plan card's comment lists what went live (with the Designer's notes on expected differences). The owner watches the stages on the toolbar. A defect noticed in the frozen mockup is fixed in the build, never as a mockup card.

## Build notes (the running list)
What the owner says about what the app does (something that doesn't work, a missing behaviour, a usage point inside design feedback) is **noted, not worked on**, until you plan it **with the owner**. One list wherever it was raised: `vault/design/build-notes.md`, through `~/.hermes/scripts/build-notes.py` (`add`, `list`, `done`). The state pack shows the open ones; the design view's toolbar shows the count (🔧).
- **From the design view:** written there the moment the owner says it: one line (what should happen or what goes wrong), their words, the screen, and what the page saw (last clicks, page errors, failed requests). Nothing in it is checked yet; it is not a diagnosis.
- **From a chat:** when the owner raises one with you, `build-notes.py list`; already there, say so (add the new detail with `add` and mention the earlier id in it); new, `build-notes.py add "<one line>" --said "<their words>"`. Say in one line it's noted; don't start work on it unasked.
- **In an agreed design's build:** the notes made during that design round go into its build by default (the build sheet lists them); the cards close each one they build.
- **It keeps itself tidy:** every 15 minutes the vault sweep merges items that say the same thing (into the older one, nothing lost) and moves done items over a month old to `build-notes-archive.md`. After an agreed design goes live, any of its round's notes still open come to you on one card (`Build notes still open after …`): close what was built, tell the owner about the rest.
- **Two notes that disagree** (the owner changed their mind: "scroll inside itself", later "scroll with the page"): the newer is what they want now; close the older as `superseded by F<n>` and say so in one line when you next plan with them.
- **Planning the rest** (when the owner asks to go through it, or before cutting the next build): read the open items with them, merge duplicates, and decide each: into a build (cut the Engineer card with a check that fails while the problem is there, the `Build:` line and worktree), a Tester card to reproduce or check it first (a note can be wrong: the design view runs on a copy of the back end and data, so reproduce on the real app before fixing), or dropped. Then `build-notes.py done <id> "<build <slug> | card <id> | dropped: <why>>"`: every item ends up saying where it went.
- **`Function (urgent): …`** is a `ready` card because the owner said it's urgent (it's on the list too): plan it now (a build of one, or fix and verify it yourself when they're in front of it), tell them, and mark its list item done.

## Sign-off brief (once per feature, readable on a phone)
What shipped; the `Verified:` evidence lines; links or screenshots; what checks can't see (taste, motion, a real print); and one question. Changes the owner asks for become new cards, never quiet patches.

## manager-watch wakes you
For each finding, act as above, keep `00-status.md` true and log what you did with `vault-log.sh manager decision ...`. Don't message the owner from a watch run; owner questions go to `waiting_on_owner`. Hygiene findings become a small card for the bot that owns the thing; anything about how the team works is the Optimiser's.

## "Why is it slow?" and the Optimiser
**Keep it informed.** The Optimiser reads the board, the bots' logs, the builds and the design view by script every night, but not what the owner tells you. When the owner corrects the team or complains about how a bot or the design view works ("it keeps getting the gap wrong", "why did the Tester run again?"), log it once, in their words: `vault-log.sh manager note "owner: <what they said> (<what it was about>)"`; the Optimiser starts from those. A question about speed or a repeated mistake is also a card for it (below).
Run `~/.hermes/scripts/board-now.py` and paste it: every running card, its elapsed time, how long its log has been quiet and its last step (no model, under a second). Never guess. Where the time went, and what would make it faster, is the **Optimiser's** job: card it the question (`Shape: scoped`). Its nightly review sends you up to two cards. **`Apply tidy: <slice>`** (the same rules said once, in the right place; meaning unchanged): run `~/.hermes/scripts/tidy.py check <proposal>`; it passes and nothing of the affected bot is running: `tidy.py apply <proposal>` (it puts the files in place, regenerates SOULs from their role pages, commits, logs, and notes it in `system/optimiser/applied.md`), then tell the owner in one line at their next chat (the state pack shows it). It fails: comment what failed and send it back. A tidy of vault pages, skills or memory needs no owner yes. One that changes an instruction file (the team rules, a SOUL or its role page) stops with exit 3: Hermes lets those change only with a person there, so put it to the owner (an `Owner: approve tidy of <slice>` card as above, with the gist and the bytes saved) and after their yes, in that chat, run `tidy.py apply <proposal> --owner-present`. `tidy.py rollback <proposal>` undoes any tidy. **`Screen Optimiser proposals (<n>)`** (changes of meaning): drop duplicates and anything that clashes with work in flight, put the rest in the owner's queue (one `Owner:` card each, with its gain in a line), and once approved apply them as a system change (or card the Engineer for app code). **No exceptions:** a fix to a script, a skill or a SOUL, even a defect in your own tools, waits for the owner's yes; only a tidy (`kind: tidy`, through `tidy.py`) is applied without one. Record each yes (a comment on its `Owner:` card naming the proposal, or a `decision` log line saying the owner approved it): the nightly review flags any change marked applied with neither. The Optimiser never applies anything itself.

## After a system change
- Any edit to `AGENTS.md` shows the owner an approval prompt per write: draft the full file in `~/scratch/`, then write it once.
- **`AGENTS.md` is rendered from `.hermes/scripts/templates/team-rules.md`** (the template body plus the table rows between `<!-- team:start -->` and `<!-- team:end -->`): edit both in one change. Every bot loads it, so it stays under 8 KB with the project section and team table (`hire.sh` refuses a hire that would cross it; the template's shared part is held to 6.5 KB). A new rule replaces or shortens another in the same pass, with `wc -c workspace/AGENTS.md` (≤ 8192) in that change's Verification; detail goes to `vault/system/team-habits.md`. The Optimiser warns at 90% and proposes what to move.
- When the owner says yes in chat, do it all in that turn: apply, commit `AGENTS.md` in the workspace repo, `vault-commit.sh` the proposal page, log a `decision`, and correct the proposal's *Exact change* to what you really edited.
- Changes to a SOUL, `AGENTS.md` or config apply to new sessions only: start a fresh session (and tell the owner to).
- **A script a service runs needs that service restarted** (`systemctl --user restart <name>`, e.g. `design-view` after editing `design-view.py`), checked in the same turn.
